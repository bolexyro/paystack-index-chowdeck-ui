Tools I did not invoke in this test

They are present in the live nine-tool catalog, but calling them would cross a user-consent boundary or require an identifier we do not have.

  • connect_merchant — sends an OTP; needs a phone number confirmed by the user.
  • quick_buy — needs a concrete purchase and can charge when confirmed.
  • order — needs a real basket; its confirmation path places the order.
  • request_transfer_approval — needs bank and recipient details and creates a transfer approval token.
  • track_order — read-only, but needs a real Chowdeck order ID from a prior purchase.
The mental model

Index is the engine. The UI is the moment.

A data tool gives the agent facts to reason over. A render tool gives the user a focused surface for the next choice. Keeping those responsibilities separate is what makes the experience composable.

Paystack Index = live commerce data

Search vendors, read menus, connect a merchant account, preview an order, place an approved order, and track delivery through the upstream MCP.

Chowdeck adapter = agent-friendly contract

Normalize Index responses, enforce safe sequencing, select only the relevant records, and attach a UI template when the user needs to decide or act.

The request lifecycle

One conversation, several small surfaces.

The agent does not dump the catalogue. It moves from evidence to a deliberate next step.

1

Orient

Start with browse_merchants; use get_balance or get_recent_activity when money or history matters.

2

Link & discover

Call connect_merchant if needed, then use find_items for a vendor or catalog.

3

Buy

Use quick_buy for featured categories or order for a long-tail merchant.

4

Approve & monitor

Use request_transfer_approval for bank transfers and track_order after a purchase.

Layer 02

The Chowdeck adapter contract

This is our narrower Chowdeck wrapper. The nine cards above are the full upstream Index catalog; these adapter tools add normalization, sequencing, and UI only where it helps.

ToolWhat it doesWhat comes back
chowdeck_browseCalls Index find_items for nearby restaurant candidates.view: "browse" + normalized restaurants. No UI template.
chowdeck_render_recommendationsRe-fetches live data and keeps only the agent’s best 1–5 vendor IDs.view: "recommendations" + restaurant cards + UI template.
chowdeck_menuCalls Index find_items for the selected vendor.view: "menu" + normalized categories and items.
chowdeck_render_menu_picksRe-fetches the menu and keeps only 1–8 matching item IDs.view: "menu-picks" + focused item cards + UI template.
chowdeck_connectStarts the phone flow or submits the OTP.view: "connect" with stage: "otp" or "connected".
chowdeck_preview_orderCalls Index order without confirmation.view: "options", "preview", or "confirm"; never charges.
chowdeck_confirm_orderConsumes the one-time preview token and sends confirmed: true.view: "tracking" after the upstream order is placed.
chowdeck_track_orderCalls Index track_order for an existing order.view: "tracking" + normalized order status.
Layer 03

Where the UI comes in

The UI is not a second Chowdeck website. It is a small surface attached to the exact tool result that needs a human decision.

One widget, many focused views.

The same app composes a different surface as the agent advances the task.

  1. 1chowdeck_render_recommendations → restaurant decision cards.
  2. 2chowdeck_menu → the selected vendor’s menu data.
  3. 3chowdeck_render_menu_picks → only the items matching “under ₦10,000”.
  4. 4chowdeck_preview_order → basket, options, delivery fee, and total.
  5. 5chowdeck_connect → phone and OTP in a focused panel.
  6. 6chowdeck_track_order → delivery timeline, not raw JSON.

// Data-only tools omit this metadata.

// The widget can compose the next step:
await window.openai.callTool(
  "chowdeck_menu",
  { vendorId: "200481" }
);
Guardrails

The rules that keep the flow useful.

These are the practical boundaries encoded in the adapter instructions and tool annotations.

Browse before render

Use live data to choose the shortlist. Never invent cards in the UI.

Keep it small

Render 1–5 restaurants or 1–8 menu items, not the whole catalogue.

Preview before place

Show options and the exact total before any confirmation-capable call.

OTP stays in UI

Keep connection details in the focused panel, not in a sprawling transcript.
